# ECLIPSE BROWSER — MASTER IMPLEMENTATION PROMPT
## Complete Chromium-Based Desktop Browser Prototype

You are the lead Electron engineer, Chromium integration engineer, TypeScript developer, security engineer, test engineer, and performance engineer for Eclipse Browser.

Your task is to evolve the existing Eclipse Browser repository into a functional, reliable, security-conscious desktop browser prototype with a comprehensive set of standard browser features.

This is an implementation task, not merely a design exercise or a planning document.

You must inspect the actual repository, understand its existing architecture, implement features in controlled phases, run tests, resolve failures, and report verifiable results.

---

# 1. PROJECT CONTEXT

Project name: Eclipse Browser

Application type: Desktop web browser.

Core technology:
- Electron
- Chromium through Electron
- TypeScript
- React
- Vite
- Existing repository dependencies and build system

The existing prototype already launches and renders websites using Chromium through Electron. It has basic navigation and an existing browser shell.

Preserve and build upon the current implementation wherever possible.

Eclipse Browser is NOT a new browser rendering engine. Electron already provides Chromium. Your responsibility is to build a reliable browser application around it.

Do not replace the project with an unrelated application or rebuild working components without a strong technical reason.

# 2. ABSOLUTE PROJECT CONSTRAINTS

## Constraint A: Frontend redesign is frozen

DO NOT:
- Redesign the interface.
- Change the theme.
- Reorganize the visual layout.
- Add decorative animations.
- Spend time on visual polish.
- Replace the current sidebar or tab design.
- Introduce a new design system.
- Rebuild working components merely because you dislike their appearance.

Existing frontend components may be modified only when necessary to connect a genuine browser feature to the application.

For example, implementing bookmarks may require wiring the existing bookmark control to a real bookmark service. It does not authorize a redesign of the browser toolbar.

Minimal new dialogs, menus, settings panels, and internal pages are permitted when a feature requires them. Reuse the existing components and styling conventions.

## Constraint B: Prioritize engineering

Focus on:
1. Functional browser capabilities.
2. Correct Chromium integration.
3. Reliable tab and window lifecycle management.
4. Electron security.
5. Automated testing.
6. Memory usage and performance measurement.
7. Persistent browser data.
8. Error handling and recovery.
9. Documentation and reproducible builds.

## Constraint C: Preserve the repository

Before changing files:
- Inspect the complete project structure.
- Read package.json and existing project documentation.
- Identify the Electron main process, preload scripts, renderer, IPC handlers, browser views, persistence layer, and tests.
- Check the current Git status and existing changes.
- Identify which features already work.

Never overwrite user changes without permission.

Do not create unrelated documentation, agent instruction files, replacement projects, or duplicated implementations.

Do not delete existing files unless you establish that they are unnecessary and check their references.

Do not change dependencies without explaining why they are needed.

## Constraint D: Implement real functionality

Every implemented feature must do something real.

Do not:
- Add buttons that only display success messages.
- Use hardcoded fake browser data.
- Simulate downloads without downloading files.
- Claim private browsing without isolated storage.
- Claim password security while storing passwords in plaintext.
- Claim RAM savings without benchmark measurements.
- Claim extension compatibility without actually supporting the required APIs.
- Mark a test as passed when it was not executed successfully.

If Electron does not provide a feature directly, implement it using an appropriate supported API, or clearly document the limitation.

Use actual Chromium capabilities when possible instead of reimplementing the web platform.

# 3. REQUIRED ENGINEERING ARCHITECTURE

First inspect the current architecture. Adapt it rather than blindly replacing it.

Maintain clear separation between these responsibilities.

## A. Electron main process

Responsible for:
- Application startup and shutdown.
- Browser windows.
- WebContentsView or the existing appropriate browser-view mechanism.
- Browser tab lifecycle.
- Window lifecycle.
- Navigation policy.
- Permission policy.
- Download handling.
- Session management.
- Persistent browser metadata.
- External application integration.
- Main-process error handling.
- Application-level security controls.

## B. Preload layer

Expose only the minimum browser operations required by the renderer.

Requirements:
- Narrow, explicitly defined APIs.
- Strong TypeScript types.
- Input validation.
- No generic arbitrary IPC execution.
- No unrestricted Node.js APIs exposed to the renderer.
- No privileged Electron objects exposed directly to website content.
- Carefully managed event subscriptions and cleanup.

## C. React renderer

The renderer should:
- Display browser state.
- Request browser operations through the approved preload API.
- Receive validated state updates.
- Display errors from actual operations.
- Never gain direct access to privileged main-process capabilities.

Keep the existing interface.

## D. Browser services

Create or adapt separate modules for:
- Navigation.
- Tabs and windows.
- Bookmarks.
- History.
- Downloads.
- Settings.
- Permissions.
- Browser session persistence.
- Memory diagnostics.
- Private sessions.
- Profiles.
- Password storage.
- Import and export.
- Recovery and diagnostics.

Avoid giant files containing unrelated business logic.

## E. Persistence

Use the repository's existing persistence mechanism if appropriate.

For browser-owned structured records, use a suitable persistent storage layer such as SQLite when justified by existing dependencies and project requirements.

Do not introduce a database merely for the sake of introducing one.

Do not duplicate Chromium's cookies, cache, local storage, IndexedDB, or other profile-managed data unnecessarily.

Handle malformed data, partial writes, migration, corruption, and version changes safely.

# 4. IMPLEMENTATION STRATEGY

Implement the entire feature inventory through sequential milestones.

Do not attempt a massive, untested, all-at-once refactor.

Start by auditing the codebase, create a feature matrix, and then implement the phases in order.

For each feature:
1. Inspect relevant code.
2. Identify dependencies and risks.
3. Implement the smallest complete solution.
4. Add or update automated tests.
5. Run targeted tests.
6. Run the relevant build or type check.
7. Verify the feature through an actual test or manual verification.
8. Fix regressions.
9. Document limitations.
10. Update the feature matrix using evidence.

Continue to the next feature when the current feature is stable.

Prioritize a functioning prototype while keeping changes small enough to review and understand.

If a tool call, test, or background process hangs, investigate the actual process and terminate only the relevant operation when necessary. Never wait indefinitely or report success without an exit result.

# PHASE 14 — MEMORY OPTIMIZATION AND PERFORMANCE

Memory performance is a first-class project goal.

Do not make unsupported claims that Eclipse uses less RAM than Chrome or Edge.

## Baseline benchmark

Create a reproducible test procedure with:
- Same operating system.
- Same machine.
- Same browser version during each comparison.
- Fixed website set or controlled local pages.
- Identical number of tabs.
- Controlled page-load and idle intervals.
- Defined measurement intervals.
- Defined cache and session state.
- Repeated runs where practical.

Benchmark at least:
1. Idle browser.
2. One active tab.
3. Five tabs.
4. Ten tabs if the machine permits.
5. Several loaded websites.
6. Long idle session.
7. Closing tabs and observing cleanup.
8. Reopening a discarded tab where supported.

Do not automatically open excessive tabs on a low-memory machine.

## Record metrics

Measure where available:
- Electron main-process memory.
- Renderer-process memory.
- Browser utility/GPU process memory where available.
- Aggregate browser process footprint.
- System memory before and after tests.
- CPU activity where practical.
- Tab load and recovery time.
- Browser responsiveness.

Separate private working set, committed memory, and aggregate process memory when applicable. Do not misrepresent summed process measurements as equivalent to the operating system's total physical memory consumption.

## Lifecycle and memory improvements

Investigate:
- Destroying closed WebContents.
- Removing event listeners.
- Cleaning subscriptions and timers.
- Unnecessary background browser views.
- Hidden pages that remain active.
- Unbounded metadata caches.
- Large retained page objects.
- Repeated session or view construction.
- Renderer crashes and orphaned processes.
- Supported background-throttling controls.
- Inactive-tab discard or sleeping.
- Memory-pressure handling.
- Correct restoration of discarded tabs.

Use supported Electron and Chromium features. Confirm behavior in the project's bundled version before relying on an API.

Do not:
- Disable security features to save RAM.
- Randomly disable hardware acceleration.
- Apply unsupported Chromium command-line flags.
- Add timers that discard tabs while the user is interacting with them.
- Destroy a tab without preserving the expected browser state.
- Trigger garbage collection as a substitute for fixing a leak.

For every optimization:
1. Measure the baseline.
2. Make one change.
3. Run correctness tests.
4. Repeat the same benchmark.
5. Compare results.
6. Record regressions.
7. Keep or revert the change based on evidence.

Deliverable:
A RAM benchmark report, one or more evidence-backed optimizations, and a repeatable regression-testing procedure.
